## 2. Log retention: default, and how to read the repo setting
- **Answer:** Default 90 days. Public repositories can set 1 to 90 days; private 1 to 400. The repository setting is read with `GET /repos/{owner}/{repo}/actions/permissions/artifact-and-log-retention`; the fine-grained token needs "Administration" repository permission (read). Responses: 200, 404. The response schema example on the same page is `{ "days": 90, "maximum_allowed_days": 365 }`; the arm check compares `days` ≥ 35 (and reads `maximum_allowed_days` only for the log).
- **Quotes:** "By default, checks, workflow runs, commit statuses, and the artifacts and log files generated by workflows are retained for 90 days before they are automatically deleted." / "For public repositories: you can change this retention period to anywhere between 1 day or 90 days." / "Starting October 1, 2026, these policies will apply to checks, workflow runs, and commit statuses in addition to artifacts and logs. Until then, checks, workflow runs, and commit statuses are retained for 400+ days regardless of your configured retention period." / Endpoint page: "Gets retention settings for checks, workflow runs, commit statuses, artifacts, and logs for a repository." / "The fine-grained token must have the following permission set: "Administration" repository permissions (read)".
- **URLs:** https://docs.github.com/en/rest/actions/permissions ; https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository ; https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-github-actions-artifacts-and-logs-in-your-organization (read 2026-10-08)
- **Effect:** Endpoint and permission in arm item 3 are verified. **New point:** as of 1 Oct 2026 (already passed) the retention setting also deletes *workflow runs*, not only logs and artifacts. If the repo's value is under 35 days, the run list the guard reads (35-day window) is shorter than the window and the back-off annotations could vanish. Arm item 3 should require `days` ≥ 35 (and at least the longest back-off/`ARCHIVE_REARM_AT` span), not just record it; refuse arming if the field is missing or smaller. The Settings path "Artifact and log retention" wording in the checklist may differ from the UI; the docs title is "Check, workflow run, status, artifact and log retention" (UI label itself UNVERIFIED).

## 3. `if: always()` after a job-level `timeout-minutes`
- **Answer:** Not stated for timeouts. Docs say a timeout makes GitHub *cancel* the job, and for a cancel, `always()` steps keep running. So it follows by reading the docs together, but no page says "always() runs after timeout-minutes": **UNVERIFIED as an explicit statement.**
- **Quotes:** timeout: "The maximum number of minutes to let a job run before GitHub automatically cancels it. Default: 360" (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax). always: "Causes the step to always execute, and returns true, even when canceled." (https://docs.github.com/en/actions/reference/workflows-and-actions/expressions). Cancellation: "To cancel the workflow run, the server re-evaluates if conditions for all currently running jobs. If the condition evaluates to true, the job will not get canceled. For example, the condition if: always() would evaluate to true and the job continues to run." and "After the 5 minute cancellation timeout period, the server will forcibly terminate all jobs and steps marked for cancellation that are still running." (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation). Read 2026-10-08.
- **Effect:** Keep the checklist's fail-closed stance (a cancelled or timed-out check stops the chain). Do not rely on an `always()` step to write a back-off annotation after a timeout. If one is needed, give that step its own shorter `timeout-minutes` and keep the job's timeout above it; any `always()` cleanup is also bounded by the 5-minute cancellation timeout.

## 5. Fork `pull_request` workflows and base-branch caches; approval setting
- **Answer:** Yes. A pull-request run can restore base-branch caches, including for forks. The approval setting is under repository Settings → Actions → General.
- **Quotes:** "Workflow runs can restore caches created in either the current branch or the default branch (usually main). If a workflow run is triggered for a pull request, it can also restore caches created in the base branch, including base branches of forked repositories." / "When a cache is created by a workflow run triggered on a pull request, the cache is created for the merge ref (refs/pull/.../merge). Because of this, the cache will have a limited scope" (https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Approval: "By default, all first-time contributors require approval to run workflows." / "Under Approval for running fork pull request workflows from contributors, choose which subset of users will require approval before running workflows on their pull requests." / options "Require approval for first-time contributors who are new to GitHub", "Require approval for first-time contributors", "Require approval for all external contributors: All users that are not a member or owner of this repository and not a member of the organization will require approval to run workflows." (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository). Read 2026-10-08.
- **Effect:** Arm item 5's premise holds, so sealing is justified. Fix the owner step's words: the setting is "Approval for running fork pull request workflows from contributors" (the sidebar section is also called "Fork pull request workflows"), and the option is **"Require approval for all external contributors"**, not "outside collaborators". Note the same page says `pull_request_target` runs always run regardless of approval settings, so the setting does not cover that trigger; the arm check on workflow triggers should refuse `pull_request_target` (and other low-trust triggers) in archive-path workflows. **API read of the approval setting:** `GET /repos/{owner}/{repo}/actions/permissions/fork-pr-contributor-approval` ("Gets the fork PR contributor approval policy for a repository."; response `{ "approval_policy": "first_time_contributors" }`). Values: `first_time_contributors_new_to_github`, `first_time_contributors`, `all_external_contributors` (https://docs.github.com/en/rest/actions/permissions, read 2026-10-08). The arm check should require `approval_policy` = `all_external_contributors`, or else give the owner the Settings step; the fine-grained token permission for this endpoint was not captured: UNVERIFIED. The dependency-caching page also describes a read-only cache default for such triggers; not needed for this checklist.
