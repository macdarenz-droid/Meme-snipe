# Design A on the tape: open questions

**Ruled.** Q2 by `../AMENDMENT_1.md`; Q1 and Q3–Q12 by `../AMENDMENT_2.md` (Q5 seed 20261009, Q11 the verdict reads count row 6, Q9 the return test frozen and built in `outcomes.py`). Readings the code takes inside the return test are listed as Q-R1-h in `research/brainstorm-loop/CODE_REDTEAM.md`.

Where the frozen design (`research/EDGE_DIALOGUE.md` "Design A", `research/brainstorm-loop/A_AMENDMENTS_ROUND7.md`) is silent or ambiguous. Each item names the reading the code uses; "conservative" marks the one picked because it makes a pass harder or keeps unknown data out. The lead or a reviewer can change any of them before the primary is scored.

1. **Placebo grid.** "20 placebo cutoffs on a log grid from 340 to 1,300 SOL, each more than 10% away from 420 and 1,470" does not say how the grid is built. Code: the smallest evenly log-spaced grid with both ends that leaves exactly 20 points after the exclusion (24 points, 4 dropped). A ratio and a log-distance reading of "10% away" give the same 20. Bands at the nearest placebos (360.4 and 482.4) do not overlap 420's bands.
2. **Supply rule, amendment (a).** The amendment asks the worker to read from the program or IDL which supply the tier rule uses. No network was allowed here. Code uses the swap event's live `base_supply` (after BOOST burns) with effective quote = vault + signed `virtual_quote_reserves`, as `packages/core/src/amm/pump-swap.ts` records for pump-amm `Pool::market_cap`. It checks this on the tape, only on fee-charging canonical SOL swaps where the live and the fixed 1B supply pick different tiers: the tier must reproduce the creator fee the program charged. On the 2 development units there were 5,565 such rows; live supply was right on 100% of them and fixed supply on 0%. Scoring refuses unless there is at least one such row and agreement is at least 99.9%. **A tape check in place of a program read needs the lead's sign-off.**
3. **BOOST window end, amendment (b).** "The end of the last `BoostBuyAndBurnEvent`" is known only when the BOOST is seen to finish. Code: the BOOST counts as finished when an event with `boost_vault_remaining = 0` is seen, and the window ends at the latest BOOST event. A pool whose BOOST events stop without that (tape coverage ended) is excluded (conservative). A pool with an `InitBoostEvent` but no BOOST event, whose coverage ends inside the first 5 minutes, is excluded too (conservative). Swaps in the same second as the window end are excluded (conservative).
4. **Tape label for BOOST swaps.** The tape README says `protocol` marks `boost_buy_and_burn`, but on the v2 development units it is 0 on every row, including the BOOST swaps. Code identifies BOOST swaps by the signature of a `BoostBuyAndBurnEvent`. This may be a decoder issue for the tape's owner.
5. **Gate statistics.** Code pools over pools: the summed seconds in each band (Gate 2), and summed creator net SOL ÷ summed hours (Gate 3), not a mean of per-pool values, which is undefined for most pools. An undefined placebo value (no time in its bands) counts as +inf, which lowers the statistic. A non-finite result for 420 counts as a fail (conservative). "95% lower bound" is taken as the 2.5th percentile of a two-sided 95% percentile bootstrap, which is stricter than a one-sided 5th percentile (conservative). It uses 10,000 pool resamples with a fixed seed. The number of resamples was not registered.
6. **What "holds until the next swap" means in data.** A swap row carries the pool's pre-trade reserves. Code: after swap i, the cap over (t_i, t_i+1) is the next swap's pre-trade state, which is the exact on-chain state over that interval and includes BOOST burns. After the last swap of a covered segment, the row's own post-trade state is used to the segment end. Base and supply are exact there; effective quote can differ slightly on v2 instructions (fee retention), and it matched the next row exactly in 81% of development pairs. Time in tape gaps is never counted.
7. **Count rule ("trade within ±5% of 420").** Code: a non-BOOST swap after the BOOST window and before hour 72 whose pre-trade cap (the cap the fee tier uses) is in [399, 441). Amendment (b) names only the gates, but BOOST pushes almost every graduate through 420 by rule, so counting those swaps would inflate the count (conservative). The upper edge is half-open, like the gate band (conservative).
8. **Gate 3 SOL measure.** "Net SOL buying" uses `quote_amount`, the SOL into or out of the pool before fees, the same on both sides. `user_quote_amount` includes fees and would tilt the measure toward buying. The creator is the row's `coin_creator`, so a change of creator is followed. Rows with the default key have no creator. Pools without creator trades stay in the denominator, as the measure is per pool hour.
9. **Return test is not frozen.** Registered: entry on the first cross of 420 from below, a stop under 399, placebo-level crosses as control, costs in SOL at $50 with the about 3.5% young-pool toll, and family membership (99.58%). Not registered: the exit rule besides the stop, the horizon, the exact stop level, the statistic, the sample floor, how the 20 placebo controls are pooled, whether entries must fall after the BOOST window, and the SOL/USD rate for $50. Code finds the cross events causally, after the BOOST window and using only the crossing row (`features.cross_events`). The outcome stage (`outcomes.py`) raises `NotImplementedError` until the test is frozen.
10. **Eligibility details.** Hour 0 is the `CompletePumpAmmMigrationEvent` time, so a pool whose migration is not in the tape is left out. Mayhem is read from the `CreatePoolEvent` in the migration transaction; if it is missing, the pool is excluded (conservative). Every swap of the pool must be canonical and WSOL-quoted. Pools whose 72 hours run past the end of the tape keep only their observed time, with no minimum. The first migration event per pool is kept.
11. **Not registered, not implemented.** The round-8 proposal in `research/brainstorm-loop/STEP_A_COUNT_ROWS.md` §6 (round-USD levels, a creator-focus split from CF) was not agreed, so it is absent.
12. **Steps.** `load.STEP_DAYS` holds Step A = 09-10 and 09-11, B = 09-07..09-09, and C = 09-02..09-06 (`research/SHARED_TAPE_PLAN.md`). The steps come from `--days`. Scoring needs the days to be exactly A, A+B or A+B+C. It reads from `--cache` only (no `--units` or `--max-units`). Each day's units must equal the planned units in `/home/user/tape-work/plan.txt` ("DAY EPOCH FROM TO"), with slot ranges contiguous from the day's first unit to its last.
